# Production remediation update — 2 November 2026

This update records the follow-up remediation to the 30 October production-readiness audit. The audit remains an historical snapshot; do not interpret this note as a production sign-off.

## Implemented in this branch

- **Partner-delegated Manager authority:** added `users.is_partner_delegate` (`2026_11_01_000002_add_partner_delegate_authority.php`) and `User::hasPartnerAuthority()`. A Partner can grant or revoke the explicit delegation from the team editor. The delegate keeps the `manager` role, cannot gain platform-admin access, cannot mint a new Partner or edit/remove a Partner account, and cannot be granted the authority until confirmed TOTP is enrolled. The UI exposes a unit selector and labels delegated accounts. Revocation is persisted and audited.
- **Delegated work scope:** privileged authority applies across the firm's units and operational controls. Attendance, leave, claims, payroll, and roster loads are scoped in database queries to the selected unit for Partners/delegates; ordinary Managers remain limited to their own unit/direct reports. Target-user guards run again on mutation, including missed-checkout and claim approval/rejection. Payroll period transitions are constrained to authorized payroll-scope users.
- **Authorization source of truth:** authenticated Manager permission checks now return only permissions from the authenticated database user record (or explicit Partner-equivalent authority); forged Livewire permission flags and `managerPermissions` cannot grant policy, payroll, final-approval, attendance, leave-review, or claim-review rights. UI/design-preview fallback is retained only for unauthenticated preview. Workflow actions use these server-backed permission helpers. Regression tests cover forged public state and DB-granted permissions.
- **Account onboarding and recovery:** invitations use a random, single-use activation token stored only as a SHA-256 hash, expire after seven days, and are consumed under a database row lock. New team/Partner accounts receive a random undisclosed password and remain unverified until activation. Team and platform password-reset actions use Laravel's throttled reset broker; passwords are never displayed or emailed, and reset revokes sessions and clears outstanding invitation tokens. Login rejects unverified accounts.
- **Privileged sign-in:** `ERP_REQUIRE_PRIVILEGED_2FA` defaults to `true`. Platform admins, Partners, and delegated Managers must have confirmed TOTP; `php artisan erp:two-factor <email>` is the operator enrolment path. Ordinary accounts remain able to sign in without TOTP. Unit tests explicitly disable this gate.
- **Runtime schema fallback:** the existing local/testing self-healing guard now includes `is_partner_delegate`; production still requires the migration rather than doing request-time DDL.
- **Regression/CI:** added grant/revoke, TOTP-before-grant, cross-unit authority, secure invitation, reset-not-password-exposure tests; CI now includes MySQL 8 feature tests and blocking Composer/npm production audits.
- **Production account changes:** sensitive self-service email/password changes require the current password; email verification is required at login. (The self-service email-change action still applies the new address immediately after current-password confirmation; a separate pending-email verification workflow remains a follow-up hardening item.)

## Release / operator requirements

1. Apply the migration with `php artisan migrate --force` before deploying code that references the delegation column.
2. Before enabling mandatory TOTP in production, enrol and confirm TOTP for **every platform admin, Partner, and Manager that will receive delegation**. If an account has no confirmed factor, password-only sign-in is intentionally rejected. Store the one-time recovery codes outside the server.
3. Verify `ERP_REQUIRE_PRIVILEGED_2FA=true`, `ERP_ALLOW_TEST_LOGINS=false`, `ERP_DEMO_MODE=false`, `APP_DEBUG=false`, and working production SMTP.
4. Send a real activation email and password-reset email; verify expiry, single-use behavior, and inbox delivery.
5. Run the full SQLite suite and MySQL job in CI, exercise the migration against a copy of the production database, rebuild/sync `public/build`, and perform the existing backup-restore and browser checks.
